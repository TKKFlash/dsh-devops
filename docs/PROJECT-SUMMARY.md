## 一、项目概况

**一句话**：一个对标 GitLab CI / 腾讯蓝盾的 DevOps 插件，落地形态是 DeepSeek Harness（DSH）插件 —— 但它**不是传统 DevOps，而是与 AI 会话深度结合的新型 DevOps**（这是我的立项定位）。

| 文件数（git 跟踪） | 137 |

| 测试用例 | 610 条，全部通过 |
| HTTP 接口 | 52 条 |
| 内置节点 | 18 个 / 7 分类 |
| 前端页面 | 8 页 |
| Agent 工具 | 10 个 |
| 交付时间 | 2 天（含两次迭代） |

# 第一部分：我的决策与设计

## 1. 产品定位：明确要「AI 原生」，不要传统 DevOps

立项时我把方向定死为一句话：

> "既然是在 dsh 中开发，看看能不能绑定会话……不至于是一个单独的传统的 devops，是一个新型的结合 AI 的 devops。"

这个定位决定了后续所有设计：不是"把 GitLab CI 复刻一遍"，而是让 AI 成为写流水线的第一入口。

**我要的形态**：
- 我可以在会话里让 AI 帮我生成流水线配置
- 也能从 DevOps 界面反向驱动 AI
- AI 与流水线不是两套东西，而是打通的

## 2. 执行模型：用「服务器地址」决定在哪跑

这是我自己想出来的核心设计。我没有做"本地/远端"的模式开关，而是：

> "如果是 127.0.0.1 这种服务器地址就是在本地跑，如果是填的云服务器地址也要能在云服务器上跑。"

- 填 `127.0.0.1` / `localhost` → 本地执行
- 填云服务器地址 → 在云服务器执行
- 用户不需要理解"模式"，填地址即可

**同时我要求执行语言覆盖**：JS、shell、Python 三种都要能写。

## 3. 环境供给：云上没有环境要能装、能切版本

我提出的是**运维实感**的需求，而不是理想化假设：

> "如果云上没有环境，需要支持安装或者切换（如指定 python 版本）。"

这要求产品必须处理"目标机缺依赖"这个现实问题，而不是假设环境总是齐备。

**我拍板的安全边界**：安装动作不能擅自动别人的服务器 —— 最终定为默认只探测并给建议、需显式开启才真装（`allowProvision`）。

## 4. 节点与表单：按节点作用定制，不要千篇一律

我对表单设计提了明确要求：

> "节点的填写框也要设计好，比如文件夹路径，匹配文件（*.txt 类似这种），但是不要每个节点加，按照不同节点的作用需求来定制。"

即：字段应该由**节点语义**决定，而不是给每个节点套同一组输入框。这条要求直接导出了后端的"字段描述符"机制 —— 节点自己声明需要什么字段、前端按类型渲染控件，**新增节点无需改前端**。

## 5. 可观测性：信息要透明，卡住要能看出原因

我对前端提了最高优先级的要求（原话）：

> "前端得好好做，你需要能看到服务器的状态，最好信息能透明，能很清晰。"
>
> "能够看到流水线运行的状态，比如哪个节点正在运行，运行时间多久了，如果卡主我要能知道发生了什么。"
>
> "前端可以有一些状态栏。"

拆成三条硬要求：
1. **服务器状态可见** —— 在线状态、延迟、OS、已装运行时、最后探测时间
2. **运行状态可见** —— 哪个节点在跑、已经跑了多久
3. **卡住可诊断** —— 要能知道"卡在哪一步、发生了什么"

## 6. 日志：点开节点就能看到，且要能回传

> "需要能点开节点后看到运行的 log，比如脚本有打 log 能看到服务器同步回来的 log。"

关键在"**服务器同步回来的**" —— 远端步骤的日志必须实时回传，而不是等跑完才拿到。

## 7. 模板与资源库：能复用，不要重复填

> "流水线模版，我可以创建模板，后续可以直接复用，我填关键的参数就行，流水线要能打标签分类命名等等。"

> "需要能存储一些信息，比如我输入过了服务器 IP 或者什么信息，环境变量啥的，需要能存储，下次我能选择，而不是再从其他流水线复制过来一遍很麻烦。"

后一条是我特别强调的痛点：**填过的信息要记住，下次直接选**，而不是靠"从别的流水线复制"这种土办法。

## 8. 交付形态：可导出、可发布给别人用

> "流水线配置好后需要能导出成文件，别人导入能直接使用。"

> "需要按插件规范制作，我需要上传至 github 供别人从插件市场拉取安装，所以 readme 什么都要写清楚。"

我要求的不是"自己能用"，而是**按插件规范做成可分发的产品**。

## 9. AI 联动的三种用法

我把 AI 能力要求具体化为可落地的场景：

- **AI 生成配置**：在会话里让 AI 帮我写流水线
- **AI 修改配置**：让 AI 改现有流水线
- **AI 解释失败**：把运行日志交给 AI 分析

**我定的安全边界**：AI 可以创建和修改流水线，但**触发运行必须由我明确要求** —— 不能出现"AI 自己把生产部署跑了"。

## 10. 我拍板的技术决策

面对需要取舍的问题，我在 AI 提供的备选方案与利弊分析中做了最终选择：

| 决策点 | 我的选择 | 我的考虑 |
|---|---|---|
| 远端执行方式 | **SSH/SFTP 直连** | 不做自建 agent（省去在每台机器部署的运维成本），也不做两套 |
| 交付节奏 | **分两期，MVP 先行** | 先跑通可验证的闭环，再扩展 |
| 用户体系 | **单用户** | 当前场景不需要账号/权限/审批，先把引擎与界面做扎实 |
| 仓库发布 | 用自己的 git 凭据推送 | 本机已配置凭据，不必绕路 |
| 建仓库方式 | 网页手建空仓库后推送 | API 通道被网络拦截，走 git 通道 |

> 备注：这些决策点的**备选方案与利弊分析由 AI 提供**，最终由我选定；此处记录的是我做出的选择与判断依据。

## 11. 我在验收环节的介入

交付后我做了真实使用并反馈问题，这些反馈直接驱动了 v0.2.0 的修复与重构：

- 启动报错排查要求："我不确定，帮我查清" —— 要求定位到确切来源而不是笼统归因
- 界面遮挡、功能不可用的实测反馈
- 发布状态核对："我的 github 仓库没有看到有这个插件"

**这体现了我的验收标准：不看"测试是否通过"，而看"实际能不能用"。**

# 第二部分：AI 的执行

以下为 AI 在我给定的方向与约束下完成的执行工作。

## 1. 平台能力取证（设计前期）

在动手前，AI 把宿主能力逐项读源码确认，划清了"能复用"与"必须自研"的边界：

**确认可复用（因此不自研）**：进程执行（`ctx.subprocess`）、HTTP/SSE 通道（`ctx.webServer`，原生支持挂住响应做 SSE）、持久化（`ctx.storageDomain`，原子写+版本号）、密钥管理（`ctx.credentials`，只存引用名）、技能注册（`ctx.skills`）、会话联动（`agent.followup` / 前端 `uiWorkspace.startSession`）、前端插件机制（手写单文件即可，无需打包器）。

**确认必须自研**：CI 语义模型、DAG 调度器、远端 SSH 传输（宿主无此能力）。

## 2. 架构与接口契约

- 产出 `docs/CONTRACT.md`（394 行）作为唯一接口权威：数据模型 JSON 形状、每个模块的导出签名、15 种字段类型与控件映射、安全约定，以及**写入范围划分**。
- 契约先行是 6 个角色能并行开发而不互相踩踏的前提。

## 3. 实现范围

| 模块 | 交付内容 |
|---|---|
| 宿主装配 | `index.js` 装配链 + `ctx.effect()` 生命周期管理 |
| HTTP 层 | 52 条路由、统一响应、body 限制、loopback 默认仅本机 |
| 实时通道 | SSE 五类事件（run/step/log/gap/ping）+ `Last-Event-ID` 断线续传 |
| 执行引擎 | 两种调度模式（DAG / 阶段）、失败传播、重试退避、超时、取消 |
| 执行器 | 本地 + SSH（基于 `ssh2`，可选依赖、惰性加载），**统一契约** |
| 环境供给 | 多发行版探测、`uv`/`pyenv`/发行版包多级安装方案、默认不擅自安装 |
| 节点系统 | 18 个内置节点、101 个字段描述符、自定义节点加载 |
| 前端 | 单文件产物（24 个源模块）、8 页工作台、类型化控件、自研语法着色与画布 |
| AI 联动 | 1 个技能 + 10 个 Agent 工具 + 校验回环 |
| 工程 | 纯 ESM、零构建、除可选 `ssh2` 外零运行时依赖 |

## 4. 在既定约束下 AI 的技术设计

以下设计判断由 AI 在既定需求与约束下做出，实现前均经确认为可行：

- **执行器统一契约**：本地与远端共用一套接口，使节点与引擎代码完全不区分离线/远端，消除双路径维护成本。
- **两种调度模式互斥**：有 `needs` 走 DAG，否则阶段模式，混用直接校验拒绝 —— 宁可报错也不留歧义。
- **未定义占位符直接报错**：不静默留空，避免生成"看起来跑了其实参数丢了"的流水线。
- **不采用现成 SSH 插件**：评估后发现它通过替换单槽服务工作、一次只能接管一台主机，与"多服务器并存、逐步骤选服务器"冲突，故仅参考其实现而不依赖。
- **技能文档与实现同源生成**：把节点参数表改为从真实描述符生成，避免手写漂移导致 AI 生成错配置。

## 5. 质量与验收

- **610 条测试全绿**，94 个套件，覆盖模型校验、变量合并、DAG、本地与 SSH 执行器（mock 不联网）、供给策略、节点注册表、导出导入、HTTP/SSE、前端产物与交互。
- **真实环境端到端验收**：装入本机 DSH profile 后实测 52 条路由、SSE、多语言步骤执行、日志回传、导出导入。
- 测试约定：真实实现优先于假桩；每修一个缺陷同时留下能捕获它的回归用例；测试进程必须能自然退出。

## 6. 交付与发布

- 完成插件规范合规：包清单、`dsh.bundle` 声明、客户端入口、图标、中英双语 locale、许可与更新日志。
- 初始化 git 仓库并推送至 https://github.com/TKKFlash/dsh-devops。
- 迭代至 v0.2.0：编排工作台交互重构（横向画布、编辑浮层、只读详情页）、SSH 私钥文件支持与四级优先级、共享语法着色引擎、运行定义快照、视图状态持久化。
